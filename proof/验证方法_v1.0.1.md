## 1. 先验证「文件没被动过」

```powershell
certutil -hashfile OurNotes-Namecard-v1.0.1.zip SHA256
```

输出（去掉空格、转小写）应等于上面那串。这一步是全部时间证明的前提 ——
时间戳只对「这一串哈希」有效，所以 zip 不要再改。

## 2. 验证 RFC 3161 时间戳（`.tsr`）

要验证签名链本身（而不只是「里面有这个哈希」），需要 openssl：

```bash
openssl ts -verify -in OurNotes-Namecard-v1.0.1.zip.tsr \
                   -data OurNotes-Namecard-v1.0.1.zip \
                   -CAfile freetsa_cacert.pem -untrusted freetsa_tsa.crt
```

看到 `Verification: OK` 即通过。

三个 `.tsr` 都验一遍（文件换成对应的 `-data`）：

## 3. 验证比特币时间戳（`.ots`）

三份证明都锚定在 **比特币区块 972187**（2026-10-19 17:49:13 UTC）。

```powershell
# 离线看证明内容（摘要 + 路径 + 区块高度），不需要节点
ots info OurNotes-Namecard-v1.0.1.zip.ots

# 重算：本地有 Bitcoin Core 节点时
ots verify OurNotes-Namecard-v1.0.1.zip.ots

# 重算：没有节点（大多数人）—— 用本目录的脚本
python ots_verify_independent.py OurNotes-Namecard-v1.0.1.zip OurNotes-Namecard-v1.0.1.zip.ots
```

`ots verify` 会向**本地 Bitcoin Core 节点**要区块头；没有节点时会直接报
`Could not connect to Bitcoin node`，这不是证明有问题。上面的脚本用公开 API
（mempool.space）取同一个区块头，我们实际跑的就是它，输出
`区块高度 972187: OK 验证通过`。

不想装任何东西：把 `<文件>` 和 `<文件>.ots` 一起上传到
<https://opentimestamps.org> 在线校验。

它做四件事：

1. 从 `.ots` 读出文件摘要和证明路径；
2. 把每条路径回溯到 Merkle 根；
3. 从 mempool.space 取回对应高度的区块头（80 字节），确认根确实在这个区块里；
4. 先确认 `.ots` 里的摘要和本地文件的 SHA-256 一致，证明这份证明不是配别的文件的。

依赖：`pip install opentimestamps-client python-bitcoinlib`。

---

## 4. 为什么两种都做

| | RFC 3161（FreeTSA） | 比特币（OpenTimestamps） |
| --- | --- | --- |
| 性质 | 权威机构签发，带 CA 链 | 去中心化，写进比特币区块 |
| 出证速度 | 秒级 | 1~2 小时（等区块） |
| 能被撤回吗 | 理论上依赖 TSA 的存续 | 不能 —— 只要比特币还在 |

两者相互独立：任何一方被质疑，另一方仍然成立。

---

## 5. 存证只证明「时间」，不证明「首创」

这一点必须说清楚，免得被误读：

* **它证明的**：在 2026-10-20 01:06（UTC+8），这些文件**已经存在**，
  而且内容就是现在这些字节。
* **它不证明的**：没有任何人在这之前做过同样的事。

「首创」是另一类主张，只能靠**检索记录**支撑。我们的检索结论写在
[`../README.zh-CN.md`](../README.zh-CN.md) 的「先行工作」一节里，
并且明确标注了检索日期。如果有人拿出更早的实现，时间戳依然成立 ——
它只是证明「我们在这天有这个东西」，而不是「只有我们有」。
